# Termin-soft

Монітор вільних термінів на порталі словацької поліції (`portal.minv.sk`).

Проблема відома: фронтенд там — це жорсткий wizard. F5 або зміна ключового
параметра вбиває стейт, і капчу зі СМС треба проходити наново. Тому тут немає
жодного `reload()`. Обидва варіанти працюють усередині вже пройденої сесії.

**Варіант 1 — `monitor.js`.** Ти один раз проходиш wizard руками, скрипт забирає
твої куки й довбить той самий XHR по колу. Капча і СМС більше не потрібні,
доки жива сесія.

**Варіант 2 — `browser-monitor.js`.** Якщо сесія вмирає швидко або токени
крутяться. Відкривається справжній Chromium, ти вводиш капчу і СМС, тиснеш
ENTER — далі скрипт смикає JS самої сторінки, без перезавантаження.

Плюс `capture-session.js` — помічник, який сам витягує потрібний запит і генерує
готовий `.env` для Варіанта 1.

---

## Коротко: що це дає і чого не дасть

Портал віддає **4 перевірки на одну капчу+СМС** (виміряно, див. нижче). Це не
обходиться — ні цим кодом, ні руками, ні жодним іншим способом. Сесія живе
близько години.

**Чого тут не буде:** цілодобового спостереження. Одна капча = одна година.

**Що тут є:** одна капча коштує тобі **один тап ≈ 30 секунд** замість трьох
хвилин уваги, і її можна зробити з телефона. 4–5 тапів на день — це 4–5 годин
покриття з будильником у Telegram.

| крок | хто робить |
|---|---|
| запустити захоплення у потрібне вікно | бот |
| заповнити анкету | бот (`ID_*`) |
| **капча** | **ти — один тап** |
| код зі СМС | бот, читає з Telegram-чату |
| вибір послуги й відділення | бот |
| 4 перевірки, рознесені на годину | бот |
| алерт: місто, дата, день тижня, через скільки днів | бот |
| **бронювання** | **ти, руками** |

Автоматизовано рівно те, чого портал не захищає. Капчу бот не чіпає, ліміт
викликів не обходить.

### Хвилі — головне налаштування

Портал **не сипле терміни випадково**. Він викидає їх пачками у конкретний
час, на фіксованій сітці. При бюджеті в чотири виклики знання цієї сітки варте
більше за всі інші налаштування разом.

```env
WAVE_TIMES=14:45        # одна відома хвиля
WAVE_EVERY_MIN=20       # інтервал сітки
WAVE_DAYS=wed           # дні, коли реліз узагалі буває
```

**Однієї відомої хвилі досить, щоб вивести всю сітку.** 14:45 на сітці в 20
хвилин — це фаза :05/:25/:45, тобто монітор сам знає всі хвилі доби.

Це міняє й розподіл бюджету. Одна хвиля на добу варта всіх чотирьох викликів.
Сітка — ні:

| | один виклик на хвилю | усі чотири на одну |
|---|---|---|
| покрито хвиль | **4** | 1 |
| покрито часу | **80 хв** — більше, ніж живе сесія | 1 хвилина |

Тому при `WAVE_EVERY_MIN` монітор ставить **один виклик на хвилю** і йде по
сітці далі, поки не скінчиться бюджет або сесія:

```
  schedule : waves every 20min, phased on 14:45 on wed
             1 check per wave, starting 10s early
             4 calls x 20min = 80min of waves covered by one CAPTCHA
             next: 14. 10. 2026 14:44:50
```

Починає за `WAVE_LEAD_MS` до часу, щоб виклик накрив реліз, а не прийшов після
нього. І попереджає, якщо найближча хвиля далі, ніж живе сесія (~55 хв) — це
була б капча, витрачена намарне.

**Звідки взяти сітку:** спитати того, хто вже ловив. Це єдина річ тут, яку не
можна вивести з коду, і вона варта більше за будь-який код.

### Готовий `.env` (допиши до того, що згенерувало захоплення)

```env
WAVE_TIMES=14:45                      # одна відома хвиля — головне; постав свою
WAVE_EVERY_MIN=20                     # інтервал сітки
WAVE_DAYS=wed                         # день релізу
WAVE_LEAD_MS=10000

ONLY_SERVICE=Registrácia              # лише потрібна послуга, не вся ротація
PREFER_OFFICE=Košice                  # перше в алерті і з зірочкою; НЕ фільтр

CALL_BUDGET=4                         # виміряно
BUDGET_WINDOW_MIN=60                  # 4 перевірки рознести на годину

SMS_CODE_VIA_TELEGRAM=true            # код зі СМС пишеш у чат бота
WATCHDOG_ON_EMPTY_POOL=true           # пустий пул не завершує монітор
CAPTCHA_WINDOWS=mon-fri 07:00-08:30, mon-fri 18:00-22:00, sat+sun 09:00-13:00

TELEGRAM_BOT_TOKEN=...
TELEGRAM_CHAT_ID=...
ID_NAME=...                           # решта ID_* — щоб анкету не набирати
```

### Щоденний цикл

```bash
npm run monitor      # хай висить; сам попросить капчу у твої вікна
npm run when         # куди ставити наступні 4 перевірки (нічого не стукає)
npm run health       # живий чи чекає на капчу
```

## Варіант 1 — API-пінгер

### Крок 1. Дістати запит

**Спосіб A (простіший) — автоматично:**

```bash
npm run capture
```

Відкриється браузер. Проходиш капчу, вводиш СМС — **і йдеш далі**: послуга →
відділення (pracovisko) → аж поки на екрані не буде **календар із датами**.
Тільки тоді ENTER.

Це найважливіше місце. Якщо натиснути ENTER раніше (наприклад на виборі
послуги), скрипт запише не той запит — потрібного просто ще не було в мережі.
У списку кандидатів дивись на мітку `[json, N dates]`: правильний той, що
віддає JSON і містить дати.

Скрипт запише:

- `.env.captured` — готовий конфіг (URL, куки, CSRF, заголовки, тіло запиту);
- `captured/requests.jsonl` — усі XHR, які робила сторінка.

Далі:

```bash
cp .env.captured .env
npm run monitor
```

Якщо він вибрав не той запит — подивись `captured/requests.jsonl` і поправ
`TARGET_URL` руками.

**Спосіб B — руками через DevTools:**

1. F12 → вкладка **Network**, увімкни фільтр **Fetch/XHR**.
2. Пройди wizard до кроку з датами.
3. Знайди запит, який повертає дати (шукай `termin`, `date`, `free` в URL, або
   просто дивись, у чиїй відповіді сидить `Nie sú momentálne dostupné...`).
4. Правий клік → **Copy → Copy as cURL**.
5. Перенеси з нього в `.env`: URL → `TARGET_URL`, метод → `METHOD`, заголовок
   `Cookie:` цілком → `COOKIE_HEADER`, CSRF-токен → `CSRF_TOKEN`
   (+ `CSRF_HEADER_NAME`, якщо він зветься не `X-CSRF-TOKEN`), `--data` →
   `REQUEST_BODY`, `User-Agent` → `USER_AGENT`, `Referer` → `REFERER`.

### Крок 2. Запустити

```bash
npm run monitor
```

Раз на 60 секунд (+ джитер) летить той самий запит. Крапка в консолі = пінг без
результату. Частіше не став — портал ріже за `CALL_LIMIT`, див. нижче. Коли з'явиться слот — банер, безкінечний біп і пуш у Telegram.

**Не закривай вкладку з wizard'ом у браузері.** Коли скрипт запищить, тобі треба
буде за секунди клікнути «Далі» саме в ній.

Скрипт зупиниться сам і скаже про це, якщо сесія помре — і коли це видно по
HTTP-статусу (`401`/`403`, редірект), і коли портал ховає це в тілі
(`{"code":"401"}` при HTTP 200). Тоді знову `npm run capture`.

## Варіант 2 — автоматизація браузера

Потрібен, якщо сесія Варіанта 1 живе занадто мало.

```bash
npm run browser
```

1. Відкриється Chromium на `START_URL`.
2. Проходиш капчу, вводиш СМС, доходиш до кроку з датами.
3. Тиснеш ENTER у терміналі.
4. Далі скрипт кожні 20 секунд змушує сторінку перепитати сервер — **без
   перезавантаження**.

### Як саме він смикає сторінку — `TRIGGER_MODE`

| Режим      | Що робить | Коли вибирати |
|------------|-----------|---------------|
| `none`     | нічого не чіпає, просто перечитує DOM | сторінка сама себе оновлює |
| `click`    | клікає `TRIGGER_SELECTOR` | є кнопка «Skontrolovať» / оновити |
| `reselect` | перемикає `<select>` на інше значення і назад | найнадійніше на цьому порталі |
| `eval`     | виконує `TRIGGER_JS` у сторінці | якщо знайшов потрібну JS-функцію |

`reselect` — це саме той трюк «клікати туди-сюди між містами»: скрипт міняє
значення випадайки на сусіднє і одразу повертає назад, кидаючи `change`. Обробник
самої сторінки робить AJAX, сесія не рветься.

Селектори треба підставити свої — подивись їх у DevTools:

```env
TRIGGER_MODE=reselect
TRIGGER_SELECTOR=select#pracovisko
API_URL_PATTERN=/getFreeTerms
SCOPE_SELECTOR=#stepContent
```

`API_URL_PATTERN` вартий того, щоб його заповнити: тоді скрипт читає JSON
відповіді напряму, а не вгадує по тексту. Це набагато надійніше.

Коли слот знайдено — біп, скріншот у `screenshots/`, вікно виводиться наперед
і **браузер залишається відкритим**, щоб ти одразу бронював.

## Як він розуміє, що слот є

Порядок перевірок (`src/detect.js`):

1. Фраза з `NO_SLOTS_TEXT` у відповіді → слотів нема. Регістр і діакритика не
   мають значення: `nie su momentalne` зловить і `Nie sú momentálne`.
2. Фраза з `SLOT_TEXT` → слот є.
3. JSON-масив дат (шлях `SLOT_JSON_PATH`, або перший знайдений масив) →
   непорожній = слот є.
4. Нічого не збіглося → **inconclusive**, скрипт скаже про це і покаже шматок
   відповіді, щоб ти поправив конфіг.

Четвертий випадок за замовчуванням не рахується слотом, щоб не будити тебе
даремно. Якщо боїшся проспати — постав `TREAT_INCONCLUSIVE_AS_SLOT=true`.

Логіка покрита тестами:

```bash
npm test
```

## Портал сам по собі падає

Зафіксовано на живому прогоні: `portal.minv.sk` був недоступний **близько трьох
годин** (46 таймаутів TCP поспіль, 20:24–23:27), тоді як сусідній
`pes.minv.sk` у тій самій підмережі відповідав нормально.

Перевірка через сторонні проксі показала в них той самий таймаут — тобто це
падіння порталу, а не блок за нашою адресою. Монітор такі збої перечікує
нескінченно: обірване з'єднання не витрачає бюджет викликів.

**Але сесія цього не переживає.** Поки портал лежить, її нічим не підтримати, і
вона протухає від бездіяльності. Коли портал повернувся, перший же запит дав
`{"code":"401"}`. Тобто після довгого простою готуйся проходити СМС наново.

## Якщо ти не вдома, лише з телефоном

Головне обмеження — сесія прив'язана до IP, а стабільний словацький IP має ПК.
Тому телефон не заходить на портал сам, а **керує браузером на ПК** через
віддалений стіл (RustDesk, для iPhone теж є). Капчу тицяєш на екрані ПК, СМС
падає на той самий телефон — код копіюєш у той самий браузер. Увесь трафік іде
з IP комп'ютера, збіг автоматичний.

Щоб віддалена сесія була якнайкоротшою, є одна команда:

```bash
npm run hunt
```

Вона відкриває браузер і чекає. Ти робиш лише те, що може людина — капча, СМС,
вибір послуги й відділення до появи дат. **Щойно дати завантажились, hunt сам**
підхоплює сесію, пише `.env` і запускає монітор. Не треба вгадувати ENTER, не
треба копіювати файли. Далі ховаєш телефон; Telegram скаже про слот або про те,
що бюджет вичерпано і час на нову капчу+СМС.

За замовчуванням hunt розтягує 6 викликів на годину — одна автентифікація
покриває годину без нагляду.

## Спершу передпольотна перевірка

```bash
npm run preflight           # чекати, поки портал оживе, потім Telegram
npm run preflight -- --once # одне вікно, вердикт, вихід 0/1
```

За замовчуванням **не завершується**, поки портал не почне стабільно
відповідати. Портал падає надовго — заміряні простої по три години — тож
корисне питання не «чи він живий зараз», а «скажи мені, коли оживе». Щойно
пройде вікно чистих запитів, прилітає пуш у Telegram із тривалістю простою.

Під час очікування невдачі не сиплються в лог щосекунди — зведення приблизно раз
на п'ять хвилин. Повернення помічається за один інтервал, а не за ціле вікно.

Смикає **тільки публічну сторінку** — ні сесії, ні бюджету викликів не витрачає.

Навіщо: дві сесії поспіль загинули однаково — знято в коротке вікно, коли
портал працював, а далі він лягав на три години, і сесія протухала, бо
підтримати її нічим. Капча і СМС — найдорожча частина, тож перевіряй **до**, а
не після.

Заміряні простої:

| період | стан |
|---|---|
| 20:24 → 23:27 | лежав, 3 год 03 хв |
| 23:27 → 00:03 | працював, 36 хв |
| 00:03 → 03:04 | лежав, 3 год 01 хв |

Уночі знімати сесію — марна трата СМС. Роби це в робочі години, коли портал
стабільний, та й терміни звільняються саме тоді.

## Перевірка стану

```bash
npm run health
```

Читає `.monitor-status.json`, який монітор переписує на кожному опитуванні.
Показує, чи живий процес, коли був останній запит, що він повернув, чи
налаштований Telegram і скільки разів ловив `CALL_LIMIT`. Жодного звернення до
порталу не робить — тобто бюджет викликів не витрачає, запускати можна будь-коли.

Код виходу 0 = все гаразд, 1 = потрібна увага.

**Це опитувальник, а не тригер.** Портал не має ні вебхуків, ні пушів — єдиний
спосіб дізнатися про термін це спитати. Монітор питає раз на `INTERVAL_MS`
(+ джитер, щоб запити не лягали ідеально рівно).

## Сповіщення

Термінальний біп марний, якщо ПК в одній країні, а ти в іншій. Постав Telegram:

1. Створи бота в [@BotFather](https://t.me/BotFather), візьми токен.
2. Напиши своєму боту будь-що.
3. Відкрий `https://api.telegram.org/bot<ТОКЕН>/getUpdates`, візьми `chat.id`.
4. Впиши `TELEGRAM_BOT_TOKEN` і `TELEGRAM_CHAT_ID` у `.env`.

Пуш прилітає і на знайдений слот, і на смерть сесії.

## Твій сетап: словацька сімка в телефоні, ПК далеко на італійському Wi-Fi

**СМС.** Словацька сімка в ЄС працює в роумінгу без доплат — код прийде миттєво.
Проблем нема.

**Італійський IP.** Ось де болітиме. `minv.sk` може віддавати `403` або
нескінченну капчу на несловацькі адреси. Ознака — `403` на першому ж пінгу
(скрипт про це прямо напише). Лікування: VPN зі словацьким або чеським сервером
на тому ПК. Важливо: **капчу і монітор треба проходити з одного IP** — якщо
сесію ти отримав з італійської адреси, а пінгувати почнеш з словацької, її
викинуть.

**Віддалений доступ.**

- Варіант 1 — вистачить SSH. Але сесію треба десь отримати: або запусти
  `npm run capture` на ПК через графічний доступ, або пройди wizard у себе на
  телефоні/ноуті й перенеси куки в `.env` руками (спосіб B вище). Другий шлях
  спрацює тільки якщо IP збігається — тобто через той самий VPN.
- Варіант 2 — потрібен графічний доступ (AnyDesk, Chrome Remote Desktop,
  RustDesk): капчу за тебе ніхто не введе.
- Якщо ПК — headless-сервер: `xvfb-run -a npm run browser` + VNC, і не забудь
  `HEADLESS=false` (за замовчуванням саме так).

**Тримай телефон зі звуком поруч** — і для СМС, і щоб не проспати пуш.

## Налаштування

Усі ключі описані в `.env.example`. Найважливіші:

| Ключ | Що це |
|------|-------|
| `TARGET_URL`, `METHOD` | той самий XHR, що віддає дати |
| `COOKIE_HEADER` | заголовок `Cookie` цілком, одним рядком |
| `CSRF_TOKEN`, `CSRF_HEADER_NAME` | анти-CSRF токен, якщо є |
| `INTERVAL_MS` | пауза між пінгами, дефолт 60000 — нижче не став |
| `NO_SLOTS_TEXT` | фрази «немає термінів», через кому |
| `SLOT_JSON_PATH` | шлях до масиву в JSON, для ECU — `services` |
| `TRIGGER_MODE`, `TRIGGER_SELECTOR` | як смикати сторінку (Варіант 2) |
| `API_URL_PATTERN` | шматок URL AJAX-запиту для підслуховування |
| `TELEGRAM_*` | пуш у телефон |

## Що з'ясувалося про сам портал

Розібрано з живого захоплення сесії (`captured/requests.jsonl`).

**Потрібна гілка — ECU**, портлет `PA_ditec-ecu-vysys`, шлях
`portal.minv.sk/wps/portal/domov/ecu/ecu_elektronicke_sluzby/ecu-vysys/`.
Це та, де «Dočasné útočisko» і «Termíny na oddelenia cudzineckej polície».
Є ще старіша `PA_ditec-vysys-01` (VYSYS01) — то універсальний рез. система
для дорожньої інспекції, не туди.

**Усі AJAX летять на ОДНУ URL.** Це WebSphere-портлет: адреса
(`!ut/p/a1/…`) не змінюється між кроками, а дія визначається тілом POST:

| Тіло запиту | Крок |
|-------------|------|
| `jsp=main1&lang=sk` | підвантаження HTML-шматка UI (не потрібен) |
| `person={…}&tida=0` | перевірка особи, у відповіді `maxTime` |
| `pincode={"pincode":"…"}&tida=0` | код зі СМС |
| `reservation={…}&tida=0&csrfToken=…&lang=sk` | список послуг, далі дати |

Крок, який **відсилає СМС**, має власний resource id:

```
.../res/id=reservation-create-pincode/c=cacheLevelPage/=/?tida=0&language=sk&kodSluzby=ECUVYSYS2-PovoleniePobytuCudzincov
POST  data={"name":"…","surname":"…","birthdate":"DD.MM.YYYY","docNumber":"…","phoneNumber":"+421…","email":"…"}
```

Тіло — це рівно те, що заповнює `src/identity.js` з `ID_*`. Відтворювати цей
запит вручну монітор не намагається: він натискає кнопки самого порталу
(`src/wizard.js`), бо вигадувати POST з реальними персональними даними в
державний бекенд — не те, що варто пробувати.

Тому для `monitor.js` `TARGET_URL` буде та сама портлетна адреса, а весь сенс —
у `REQUEST_BODY`. **CSRF-токен тут іде полем у тілі, не заголовком.**

**Справжні фрази «немає термінів»** — витягнуті з JS порталу, вони вже стоять
дефолтом у `src/detect.js`:

- `noDatesAvailable` — «Nie sú momentálne dostupné žiadne termíny. Skúste to prosím neskôr.»
- `noAvailableSlots` — «Vo zvolenom dátume nie je prístupný žiaden voľný termín…»
- `missDate` — «Pre zvolené pracovisko nie je k dispozícii žiadna voľná rezervácia.»
- `missTime` — «Pre zvolený deň nie je k dispozícii žiadna voľná…»

**Сесія живе ~45 хвилин.** Відповідь на крок `person` містить `maxTime` — це
дедлайн. Після нього тільки заново з капчею і СМС.

**Капча — reCAPTCHA Enterprise v2** (`recaptcha-v2-verify`). Обійти її скриптом
не вийде і не варто пробувати — саме тому обидва варіанти розраховані на те, що
ти проходиш її руками один раз.

## Сесія прив'язана до IP — це головна пастка

Портал явно фіксує твою адресу: сторінка сама питає її в `api.ipify.org` і
шле на `GetIpAddress` / `test`. Якщо VPN увімкнений **тільки в браузері**, то
`monitor.js` стукатиме з іншої адреси, ніж та, до якої прив'язана сесія, — і
його викинуть.

Саме це й сталося при першому захопленні: браузер бачив `84.245.121.110`
(Словаччина), а Node виходив через `151.70.24.101` (Італія).

`capture-session.js` тепер сам порівнює обидві адреси й голосно попереджає про
розбіжність. **VPN має бути системний**, а не браузерний.

## ГОЛОВНЕ: бюджет — 4 відповіді на сесію

Виміряно 2026-10-05 на трьох сесіях поспіль: чотири відповіді, п'ятий запит —
`CALL_LIMIT`. Однаково з перебудовою контексту візарда і без неї.

**Практичний наслідок, який варто прийняти одразу:** одна капча + СМС дають
**чотири перевірки**, і сесія так чи так не переживе години. Цілодобового
спостереження без нагляду тут не побудувати — ні цим кодом, ні жодним іншим,
бо захист стоїть саме проти цього. Реалістична мета — **4 влучні перевірки у
правильну годину**, а не постійне чергування.

Що перевірялось раніше, по черзі:

| що пробували | результат |
|---|---|
| рідше опитувати (6 с → 60 с) | `CALL_LIMIT` на тому самому ~6-му виклику |
| чергувати 9 різних `serviceBranchID` | те саме |
| унікальний URL на кожен запит (`_=timestamp`) | те саме |
| перечекати 10 хв після `CALL_LIMIT` | наступний виклик = `401`, сесія мертва |

Отже: **сесія дозволяє близько шести звернень** до
`available-offices-service-date`, і далі її розлогінює. Ні пауза, ні варіювання
запиту, ні очікування нічого не змінюють. Портал захищений саме від опитування,
і захист працює.

Підтвердження з іншого боку: браузер за весь візард викликає цей ендпоінт
**рівно один раз**.

**Що це означає на практиці:** одне СМС = 4 перевірки. Три гіпотези, які
лишались неперевіреними, тепер виміряні — дві спростовані, одна ще жива.
Деталі нижче.

### Як витиснути з цього максимум

Якщо відповідей лише чотири — не пали їх за чотири хвилини. Розтягни на вікно:

```env
CALL_BUDGET=4
BUDGET_WINDOW_MIN=60     # 4 перевірки на годину = раз на 15 хв
```

Монітор сам порахує інтервал. Найкраще запускати перед моментом, коли терміни
зазвичай звільняються, — тоді шість перевірок накриють саме те вікно.

## Що ще не перевірено щодо бюджету

Усе з таблиці вище перевірено й не працює. Але є три речі, яких ніхто не
пробував, і всі вони **вимірювані, а не хитрі**. Жодна не чіпає ні капчу, ні
СМС, ні IP, ні чужі дані — усі вони повторюють власні кроки порталу з власними
тілами запитів порталу.

Кожна пише свій результат у `EXPERIMENT_LOG` (типово `experiment.jsonl`), бо
відповідь має пережити сесію, яка її дала. Саме через брак такого логу бюджет у
цьому репозиторії описаний то як «~4», то як «~6».

```bash
npm run experiment        # вердикт по логу: скільки викликів дала кожна сесія
```

### Гіпотеза 1: лічильник прив'язаний до контексту, а не до сесії — **СПРОСТОВАНА**

Виміряно 2026-10-05, три сесії:

| сесія | запитів дат | оновлень кроку послуг | померла на |
|---|---|---|---|
| s2 8:51 | 5 | 0 | 38 хв |
| s1 10:08 | 5 | 0 | 31 хв |
| s1 11:20 | 5 | **1** | 40 хв |

П'ятий запит у кожній — це вже `CALL_LIMIT`. Тобто **чотири відповіді на
сесію**, і оновлення кроку послуг не змінило нічого.

Найцікавіше — що механізм **спрацював**: о 11:50 крок послуг повернув
справді новий `serviceBranchID` (`fb8d59de-…`), тобто сервер дійсно будує
новий контекст. І лічильник це пережив. **Отже лічильник прив'язаний до сесії
(куки), а не до контексту візарда і не до ID послуги.**

Побічно це закриває і стару розбіжність «~4 чи ~6»: бюджет — **4**.
`CALL_BUDGET` тепер типово 4.

Оновлення не з'їдає бюджет дат (4 з ним і 4 без), тож `SERVICES_REFRESH=true`
не шкідливий — просто безкорисний. Код лишається, щоб вимір можна було
повторити, якщо портал зміниться.

Нижче — як це перевірялось, на випадок повторного заміру.

#### Початкова гіпотеза

Чому правдоподібно:

- браузер за один прохід wizard'а викликає ендпоінт дат **рівно один раз**, і
  завжди **після кроку послуг**;
- `serviceBranchID` генеруються щоразу заново, тобто на цьому кроці сервер
  створює новий контекст;
- витрачена сесія віддає `{}` (`src/portal.js`) — це означає саме «контекст
  втрачено», а не «логін недійсний».

Якщо так, то схема «3 запити дат → крок послуг → ще 3 → …» не впреться в
`CALL_LIMIT`.

**Спершу перевір руками, це одна СМС і жодного рядка коду:**

1. Дійди до дат, відкрий DevTools → Network, фільтр Fetch/XHR.
2. Тисни «Späť» до вибору послуги, вибери **ту саму** послугу, дійди до дат.
3. Повтори 8–10 разів.
4. Дивись: чи кожного разу йде `available-agenda-services`, і чи **після 6-го
   разу дати ще приходять**.

Якщо приходять — гіпотеза підтверджена, і в моніторі вона вже реалізована:

```env
SERVICES_REFRESH=true
SERVICES_REFRESH_EVERY=3     # крок послуг після кожних 3 запитів дат
SERVICES_REFRESH_GAP_MS=2000 # людська пауза між кроком і запитом дат
```

Сесія зберігає URL, тіло й токен кроку послуг (`servicesStep` у
`sessions.json`, або `SERVICES_STEP` у `.env` для одиничної сесії) — це пише
`npm run capture` і `npm run hunt` самі. Монітор повторює цей крок і бере з
відповіді **новий ID потрібної послуги**: за назвою, не за ID, бо ID
перевидаються. Темп між парами «крок послуг + запит дат» лишається
`INTERVAL_MS`, тобто людський.

**Чи коштує оновлення одного виклику — теж не перевірено.** Крок послуг має
інший resource id (`id=reservation`), ніж ендпоінт дат
(`id=available-offices-service-date`), а `CALL_LIMIT` ловили **тільки на
другому**. Тому можливі три результати, і `npm run experiment` їх розрізняє:

| Що в лозі | Висновок |
|---|---|
| запитів дат значно більше за `CALL_BUDGET` | гіпотезу підтверджено, знижуй `SERVICES_REFRESH_EVERY` |
| запитів дат ≈ `CALL_BUDGET`, оновлення зверху | не підтверджено, але оновлення безкоштовне |
| запитів дат + оновлень ≈ `CALL_BUDGET` | не підтверджено, і лічильник спільний — **вимикай**, воно їсть бюджет |

Через цю невизначеність за замовчуванням **вимкнено**.

### Друга межа — вік сесії ~62–65 хвилин. І вона, можливо, та сама

Три сесії, знятих 15:45, 15:46 і 15:48, перейшли з `{"services":[]}` на `{}`
між своєю 62-ю і 65-ю хвилиною (деталі в `src/portal.js`). Це вік, а не
випадковість.

**Наслідок, про який легко забути:** пул, знятий за один раз, помирає теж за
один раз. Три сесії підряд не дають трьох годин — вони дають одну годину з
утричі щільнішим опитуванням. Для «відійшов на пари» це не рятує.

**Але `{}` означає «контекст втрачено»** — рівно те, що, за гіпотезою 1,
створює крок послуг. Тобто обидві межі можуть бути однією: не «сесія живе
годину», а «контекст живе годину». Якщо повтор кроку послуг перебудовує
контекст, він може перезапустити і годинник.

Це єдине, що може зробити роботу без нагляду можливою взагалі — усе інше
впирається в одну капчу на годину. `npm run experiment` розділяє віки сесій на
«з оновленнями» і «без», і прямо каже, зламана стеля чи ні:

```
Age at death — can a session outlive the ~65 minute ceiling?
  without refreshes: 63min (calls)
  with refreshes   : 140min (age)
  A refreshed session reached 140 min — the hour ceiling is NOT fixed.
```

Сесію, яка померла від `CALL_LIMIT` на 14-й хвилині, за доказ не рахує — вона
до стелі просто не дожила.

### Гіпотеза 2: браузер сам витрачає твій бюджет — **не підтвердилась**

Припущення було: кожен клік між послугами у wizard'і — це ще один запит дат, і
саме тому бюджет описаний то як «~4», то як «~6».

Перевірено на живому лозі захоплення (2026-10-05):

```
captured/requests.jsonl
  requests recorded   : 21
  services steps      : 1
  date endpoint calls : 1
```

**Один виклик за весь прохід** — це мінімум, менше неможливо. Отже клікання
між послугами розбіжність не об'ясняє. Одне захоплення (n=1), але воно ж і
підтверджує старе спостереження: за весь візард ендпоінт дат викликається
рівно раз.

Перевіряти варто й далі — якщо колись знову здасться, що бюджет менший за
очікуваний, це перше, що треба виключити, і це безкоштовно.

```bash
npm run audit                          # captured/requests.jsonl
npm run audit -- a.jsonl b.jsonl       # кілька сесій одразу
```

Рахує виклики ендпоінта дат у логах захоплення — нічого не стукає в портал.
`npm run capture` тепер ще й лічить їх уголос під час проходу:

```
  [200] POST .../res/id=available-offices-service-date/...
     ^^ date endpoint, call #2 of this session's budget
     !! going back and forth between services spends calls. Pick once, then stop.
```

**Висновок на практиці:** під час захоплення не клікай між послугами. Вибрав —
іди далі.

### Гіпотеза 3: `tida=0` — це ідентифікатор вкладки

Якщо сервер тримає стан окремо для кожної вкладки, то `tida=1` може мати свій
лічильник. Імовірність низька, але витрачена сесія нічого не варта, тож і
перевірка безкоштовна: після `CALL_LIMIT` монітор перепитує ту саму сесію під
кожним із цих значень, і лише потім ховає її.

```env
TIDA_RETRY_VALUES=1,2
```

## Що тут автоматизовано, а що ні

Портал дає **4 перевірки на одну капчу+СМС**, і це не обходиться. Тому дефіцитний
ресурс тут — не запити, а **твоя увага**. Правильна метрика: скільки секунд
уваги коштує одна година спостереження.

| крок | хто робить |
|---|---|
| запустити захоплення | бот, за розкладом |
| заповнити анкету | бот (`ID_*`) |
| **капча** | **ти — один тап** |
| код зі СМС | бот, з Telegram-чату |
| вибір послуги й відділення | бот |
| 4 перевірки + будильник | бот |
| бронювання | **ти, руками** |

Один тап ≈ 30 секунд, і його можна зробити з телефона через віддалений стіл.
4–5 тапів на день — це 4–5 годин покриття на добу. Усе, що портал захищає
(капча, ліміт викликів), лишається недоторканим; автоматизовано тільки те, що
він не захищає.

### Розклад: `CAPTCHA_WINDOWS`

Раніше наглядач просив капчу щойно здихав пул — міг і о третій ночі. Тепер він
питає лише у вікна, коли ти можеш відповісти:

```env
CAPTCHA_WINDOWS=mon-fri 07:00-08:30, mon-fri 18:00-22:00, sat+sun 09:00-13:00
```

Поза вікнами монітор мовчить і чекає. Банер друкує, скільки годин на тиждень
розклад покриває — при ~1 годині на капчу це і є стеля покриття.

### Алерт читається за секунди

Раніше в Telegram летів сирий JSON із `branchPublicId`. Тепер:

```
🚨 TERMÍN AVAILABLE 🚨
Dočasné útočisko / Registrácia
★ KOŠICE — 27.10.2026 (вт) — через 22 дн.
★ KOŠICE — 29.10.2026 (чт) — через 24 дн.
  SNINA — 20.10.2026 (вт) — через 15 дн.
👉 https://portal.minv.sk/...
```

`PREFER_OFFICE=Košice` ставить потрібне місто першим і позначає зірочкою. Це
**не фільтр** — слот будь-де кращий за жодного, тож будильник дзвонить завжди.

Дні тижня в алерті не випадкові: заяву на тимчасовий притулок приймають лише у
вівторок і четвер, тож усі терміни будуть саме такі.

## Наглядач: пустий пул більше не завершує монітор

Раніше, коли всі сесії вичерпувались, монітор виходив — і єдине, що могло
крикнути про слот, зникало саме тоді, коли це найпотрібніше.

Тепер (`WATCHDOG_ON_EMPTY_POOL=true`, за замовчуванням) він:

1. пише в Telegram «потрібна капча + СМС»;
2. відкриває вікно й сам заповнює анкету (`ID_*`);
3. чекає, поки ти пройдеш капчу — її він не торкається, це захист порталу;
4. бере код зі СМС (див. нижче) і вводить його;
5. сам вибирає послугу (`ONLY_SERVICE`) і відділення (`OFFICE`);
6. щойно пішов запит дат — підхоплює сесію в пул і **продовжує опитування**.

**Порядок тут важливий, і один раз він був зламаний.** СМС з'являється лише
після капчі, тому прохання ввести код приходить **тільки** тоді, коли портал
справді відрендерив поле для нього. 2026-10-05 було не так: поле для коду
шукалось за словами `pin`/`kod`, і речення самого кроку 1 — «na Vaše telefónne
číslo bude zaslaný PIN kód» — під них підійшло. Через це монітор вирішив, що
крок уже пройдено, капчу не чекав, «Pokračovať» не натиснув, анкета не
відправилась, СМС не прийшла — а в Telegram полетіло «напиши код зі СМС».

Тепер крок визначається **станом, а не формулюванням**: поки на сторінці є
анкета, жодна назва не вважається полем для коду. Якщо поле все одно не
знаходиться — `PIN_SELECTOR=<css>` у `.env`. І при будь-якій невдачі кроку
сторінка зберігається в `captured/relogin-<крок>-<час>.html`, щоб селектор
правився за фактом, а не вгадувався (там персональні дані — каталог у
`.gitignore`).

Якщо браузер відкрити не вдалося (headless-сервер, немає дисплея) або
щось у wizard'і зсунулось — монітор не падає, а **чекає на нову сесію у
`sessions.json`**. Тобто `npm run capture` в іншому вікні підхоплюється без
перезапуску, а вікно наглядача лишається відкритим, щоб ти міг докінчити крок
руками.

`npm run health` показує такий стан окремо — `WAITING FOR A SESSION`, а не
«завис».

### Код зі СМС через Telegram-бота

Код приходить на телефон, wizard — на ПК. Щоб не тягнути для цього віддалений
стіл, монітор читає код із того самого чату, куди шле сповіщення про слоти:

```env
SMS_CODE_VIA_TELEGRAM=true
SMS_CODE_TIMEOUT_MS=600000
```

Прилетить «📲 Напиши код зі СМС сюди в чат» — відповідаєш 4–8 цифрами, і їх
вводять у форму. Читається **тільки твій чат** і **тільки повідомлення, надіслані
після запиту**: старий код з історії все одно протух, а використати його означало
б змарнувати капчу.

Ввести код руками у вікні можна завжди — цей шлях нікуди не зник.

У підсумку від тебе лишається один клік у капчі приблизно раз на годину.

### Чого тут свідомо немає

Сервісів, що розв'язують капчу за тебе, ротації IP, чужих SIM-карток і чужих
даних. Це прямий обхід захисту порталу. До того ж сесія прив'язана до IP, а
стоїть reCAPTCHA Enterprise разом з v3 — ризик заблокувати свій номер, свій IP
або себе як заявника набагато дорожчий за будь-який виграш.

## Портал ховає помилки в тілі, а не в статусі

Найпідступніше з усього. Обидві ці відповіді приходять з **HTTP 200**:

| Тіло | Що насправді |
|------|--------------|
| `{"code":"401"}` | сесія мертва |
| `{"code":"500","message":"CALL_LIMIT"}` | ліміт запитів |
| `{"services":[...]}` | справжні дані |

Якщо дивитися лише на HTTP-статус — а саме так робила перша версія — мертва
сесія виглядає як звичайна порожня відповідь, і монітор нескінченно доповідає
«вільних немає». Тепер тіло розбирає `src/portal.js`, і це покрито тестами.

## Ендпоінт дат для ECU

```
.../ecu-vysys/!ut/p/a1/…/res/id=available-offices-service-date/…?tida=0&language=sk&kodSluzby=ECUVYSYS2-PovoleniePobytuCudzincov
```

- метод `POST`
- тіло `data={"serviceBranchID":"<id послуги>","authValue":"false"}`
- відповідь `{"services":[...]}` — **порожній масив означає, що вільних термінів нема**
- тому `SLOT_JSON_PATH=services`

ID послуг (з групи `217` «Termíny na oddelenia cudzineckej polície» і `242`
«Dočasné útočisko») лежать у відповіді попереднього кроку — `capture-session.js`
їх запише в лог.

`maxTime` у відповіді на крок з особою — це **не** час смерті сесії. Перевірено:
пінги проходили і після нього. Схоже, то дедлайн на завершення бронювання.

## Чому TLS ламався (виправлено, але варто знати)

`pes.minv.sk` віддає **тільки листовий сертифікат** — без проміжного
`CA Disig R2I2 Certification Service`. Браузер це не помічає, бо довантажує
проміжний сам через AIA. Node так не вміє, тому `monitor.js` падав з
`UNABLE_TO_VERIFY_LEAF_SIGNATURE` — при тому, що сертифікат абсолютно валідний.
Для порівняння, `portal.minv.sk` і `www.minv.sk` віддають повний ланцюг із трьох.

Полагоджено файлом `certs/ca-disig.pem` — він підвантажується автоматично і
дає Node той ланцюг, який мав прислати сервер. Корінь `CA Disig Root R2` Node
довіряє й так, тому перевірка лишається **повноцінною**: це не
`rejectUnauthorized: false` і не вимкнена валідація.

Якщо колись впреться в той самий `UNABLE_TO_VERIFY_LEAF_SIGNATURE` на іншому
хості — скрипт сам підкаже, а сертифікат підставляється через `EXTRA_CA_FILE`.

## Що вже перевірено на цьому ПК

- Node 24.12, git 2.52, Chromium для Playwright — стоять.
- `npm test` — 11/11 зелених.
- `monitor.js` проти локального фейкового порталу: ловить слот, коректно вмирає
  на 403.
- `browser-monitor.js` через `reselect`: смикає AJAX без перезавантаження, читає
  JSON, робить скріншот.
- `capture-session.js`: знаходить потрібний XHR серед решти, витягує куки й CSRF,
  пише робочий `.env.captured`.
- Доступ до порталу з цього IP (Італія, `151.70.24.101`): **є**, без 403 і без
  Cloudflare. VPN поки не потрібен — але капчу проходь з того ж IP, з якого
  потім пінгуватимеш.
- `monitor.js` проти живого `pes.minv.sk`: TLS проходить, на підроблену сесію
  сервер дає 302, скрипт це правильно розпізнає як «сесію треба переробити».

## Кілька зауважень

- **Не став `INTERVAL_MS` нижче ~10 секунд.** Швидше слоти не з'являться, а от
  рейт-ліміт або бан IP — цілком. 15 секунд це вже частіше, ніж встигає
  оновлюватися черга.
- **`.env*` і `captured/` не комітяться** (`.gitignore`) — там живі куки твоєї
  сесії, це фактично твій логін.
- **`captured/requests.jsonl` містить персональні дані** — ПІБ, дату
  народження, номер документа, телефон, email і PIN зі СМС. Воно потрібне лише
  щоб зібрати `.env`. Зібрав — видали каталог.
- **`experiment.jsonl` персональних даних не містить** — тільки мітки сесій,
  вік, кількість викликів і вердикти. Його можна показувати й вставляти в
  переписку. Теж у `.gitignore`, щоб не шуміти в історії.
- **`_cp.json` видалено з репозиторію**: там лежало тіло запиту
  `reservation-create-pincode` разом з ПІБ, датою народження, номером
  документа, телефоном і email. Такі чернетки тепер теж у `.gitignore`
  (`_cp*.json`). **Файл лишається в історії git** — якщо її треба переписати,
  це окрема дія з force-push, роби свідомо.
- **Куки протухають.** Зазвичай 15–30 хвилин без активності. Сам цикл пінгів
  тримає сесію теплою, але вічно вона не проживе — перезнімай через
  `npm run capture`.
- Скрипт **нічого не бронює автоматично**. Він тільки кричить, коли слот
  з'явився; останній клік за тобою. Так і задумано: помилкове автобронювання
  спалить твою чергу.
